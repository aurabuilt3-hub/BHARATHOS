# BharatOS Authentication & Authorization System

This document outlines the authentication flows, profile synchronization model, role-based access control (RBAC), and geographic scope validation rules implemented in the BharatOS backend.

---

## 1. Authentication Flow

BharatOS relies on **Supabase Auth** as the primary identity provider (IdP) for handling user signups, sign-ins, and token issuance. The backend validates and decodes the JWT claims generated by Supabase.

```
+------------+          (1) Signup / Signin          +----------------+
|            | ------------------------------------> |                |
|  Next.js   |                                       | Supabase Auth  |
|  Frontend  | <------------------------------------ |                |
|            |             (2) Bearer JWT            +----------------+
+------------+
      |
      | (3) POST /auth/sync-profile (with JWT)
      v
+------------+          (4) Validate JWT Claims          +----------------+
|  FastAPI   | ------------------------------------> |  Supabase SDK  |
|  Backend   | <------------------------------------ |   get_user()   |
+------------+                                       +----------------+
      |
      | (5) Create/Update local database user record
      v
+------------+
| PostgreSQL |
|  Database  |
+------------+
```

### Profile Sync Strategy
- **JWT Verification**: `get_supabase_user` extracts the JWT token from the `Authorization` header, validating it via Supabase to retrieve user email and ID claims.
- **PostgreSQL Resolution**: `get_current_user` matches the Supabase UID to local users.
  - If a user is authenticated but not registered locally, the backend returns a strict `404 Not Found` response.
  - Profile registration/syncing is handled by `POST /auth/sync-profile` (and `POST /users/profile`).

---

## 2. Privilege Escalation Prevention

To prevent users from modifying their privileges:
- **Role Assignment**: Signup payloads are strictly mapped to the default `"citizen"` role unless pre-provisioned via secure administrator interfaces.
- **Geographic Scope**: Client payloads attempting to specify `state_id`, `district_id`, or `city_id` during signup sync are ignored. All scopes default to `null` on new user registration.
- **Updates**: Profile sync operations on existing users update only safe metadata fields (`full_name`, `phone`) and leave credentials, roles, and geographic scopes unaltered.

---

## 3. Role-Based Access Control (RBAC)

FastAPI dependencies restrict endpoints by checking role names on resolved users:
- `require_role(role)`
- `require_roles([role1, role2, ...])`

### Roles Catalog
1. **citizen**: Standard public interface (default role). Can report incidents and query municipal assets.
2. **officer**: Department dispatch/responder.
3. **dept_head**: Department command level.
4. **state_admin**: Regional administrative oversight.
5. **admin** / **national_admin**: Platform-wide operational access.

---

## 4. Geographic Scope Hierarchy

Geographic scope boundaries limit data visibility and command control. Scope is checked using `verify_geographic_scope(user, target_state_id, target_district_id, target_city_id, db)`:

```
National (admin, national_admin)
   |
   +---> State (state_id)
            |
            +---> District (district_id)
                     |
                     +---> City (city_id)
```

- **National Admins**: Access state, district, city, or general resource bounds.
- **State Operators**: Access assets matching their `state_id`, or child districts/cities within their state. Reject access to other states.
- **District Operators**: Access assets matching their `district_id`, or child cities within their district. Reject access to state-wide or other district resources.
- **City Operators**: Access assets matching their `city_id` only. Reject access to district-wide, state-wide, or other city resources.
